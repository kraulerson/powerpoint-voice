# Agent Result — presenter-flow (UAT Session 3)

**Summary:** I built a Qt harness in the scratchpad that links the real `pptv_ui`/`pptv_core` static libraries and drives the real `AppShell` + `PresentationWindow` with `QTest::keyClick` against real .pptx decks, then screen-scrapes the actual `SlideSurface` pixels to answer "what is on the projector right now?" independently of what the controller believes. 33 scenarios, each in its own process so a crash cannot hide the rest. Harness: /private/tmp/claude-501/-Users-karl-Documents-Claude-Projects-powerpoint-voice/05a4d2ab-f2bc-4839-9c01-2ee22b3c3560/scratchpad/harness/presenter_harness.cpp; decks generated by .../scratchpad/gen_decks.py; results in .../scratchpad/out/. Baseline `ctest` is 178/178 green and the shipped binary does present a deck correctly.

Every finding is in the wiring (AppShell / PresentationWindow / main.cpp), not in the tested leaves — as predicted. Three matter for 2026-08-10: (1) `AppShell::teardownWorkers()` aborts the process with SIGABRT whenever a slide render outlives its 5 s wait — the "bounded shutdown" comment claims to avoid exactly the qFatal it actually triggers; (2) the Esc privacy blackout un-blanks itself the moment the pre-render worker delivers the slide the presenter is standing on, putting the deck back on the projector during Holding *and* behind the quit prompt; (3) on a MacBook + 1080p projector the deck is letterboxed twice and covers only 75 % of the projector — and this is invisible in rehearsal because it only appears when a second screen of a different aspect is attached.

I could not break the parts the previous audit hardened: no SEGV across pre-render completion (40 rounds of key hammering), no cross-deck content leak (8 rounds of mid-render deck switching), no path or deck content in any dialog or notice, Esc never closes the window, 30 Escapes never quit, and the screen matched the controller's index at every step of a full 10-slide talk.

## Findings (10)

### [SEV-1] AppShell::teardownWorkers() aborts the app (SIGABRT) whenever a slide render outlives the 5 s wait — hit by quitting OR by opening a second deck

**Repro:** cd /private/tmp/claude-501/-Users-karl-Documents-Claude-Projects-powerpoint-voice/05a4d2ab-f2bc-4839-9c01-2ee22b3c3560/scratchpad
# decks/vslow3.pptx = 3 slides x 1990 shapes — UNDER the TM-018 caps (2000 shapes / 5000 runs), ~34 s/slide
./harness/b/presenter_harness "$PWD/decks" s23    # quit the app mid-render   -> exit=134
./harness/b/presenter_harness "$PWD/decks" s23b   # open a SECOND deck mid-render -> exit=134
./harness/b/presenter_harness "$PWD/decks" s23c   # instrumented

Both print:  QThread: Destroyed while thread '' is still running   and exit with 134 (SIGABRT).
s23c prints the mechanism directly:
  >>> teardownWorkers blocked the UI thread 6015 ms
  >>> after wait(5000)+terminate()+wait(1000): thread object=alive isRunning=1 isFinished=0 worker=alive
  [FAIL] the render thread actually stopped before deleteLater() was posted on it

Mechanism, src/ui/app_shell.cpp:71-85 — `if (!t->wait(5000)) { t->terminate(); t->wait(1000); } t->deleteLater();`
On macOS QThread::terminate() is pthread_cancel, and a thread inside QPainter/CoreText has no cancellation point, so it keeps running (isRunning=1 above). deleteLater() then posts a deferred delete, the event loop runs ~QThread on a live thread, and Qt qFatal()s — the exact abort the comment on line 78-79 says it is avoiding.

**Impact:** Karl swaps to a second deck at the podium, or presses Esc-Esc-Ctrl+Shift+Q to end the talk, while any slide is still rendering past 5 s: the UI freezes for a hard 6 seconds and then the process dies with a macOS crash report in front of the audience. Reachability is gated on a single slide taking >5 s to render — unlikely for a plain 10-slide text deck, but BUG-21 (known-deferred) explicitly states an under-cap slide can take minutes, and this is what happens when it does: not graceful degradation, an abort. Even without the abort, the 6 s UI freeze on every deck swap is itself a stage failure.

**Fix:** Do not terminate()+deleteLater() a QThread. Make the render loop actually stop: PreRenderWorker::renderOne() already knows the per-slide elapsed time, so check cancelled_ inside the paint loop (and cap per-slide work), then join normally. If a hard bound is still wanted, keep the thread and worker alive and leak them deliberately (park them in a detached list) rather than destroying a running QThread — `t->deleteLater()` must be reached only on the `wait()` success path. Also stop calling teardownWorkers() synchronously from openDeck(): tear down asynchronously so the UI thread never blocks on a worker.

### [SEV-2] The Esc privacy blackout un-blanks itself: onSlideReady() paints the deck back onto the projector while the controller is still in Holding (and behind the quit prompt)

**Repro:** cd /private/tmp/claude-501/-Users-karl-Documents-Claude-Projects-powerpoint-voice/05a4d2ab-f2bc-4839-9c01-2ee22b3c3560/scratchpad
./harness/b/presenter_harness "$PWD/decks" s5d   # simplest: walk forward, Esc, wait
./harness/b/presenter_harness "$PWD/decks" s5b   # jump to an unrendered slide, then Esc
./harness/b/presenter_harness "$PWD/decks" s5c   # same, but under the quit prompt
./harness/b/presenter_harness "$PWD/decks" s5e   # on a REAL-SHAPED 10-slide deck

s5d output (decks/slowbright16.pptx — every slide a flat colour so the pixels are unambiguous):
  ...  standing on slide 9, raster null=1
  [PASS] Holding
  [PASS] blank
  >>> lit=0.562 dominant=#0080ff brightSlide=9 mode=Holding
  [FAIL] still blank after the renderer caught up (lit=0.5625)

s5c (quit prompt up):  >>> AFTER delivery: mode=ConfirmQuit lit=0.562 dominant=#80ff00 brightSlide=10
s5e on the 10-slide deck: reproduced on the COLD round in both runs —
  >>> round 0: Esc blanked the projector, then slide 1 re-appeared while mode=Holding

Mechanism, src/ui/app_shell.cpp:211-220 — onSlideReady() calls showSlide() directly:
    if (index == controller_.currentIndex0Based()) { showSlide(controller_.currentSlide1Based()); }
showSlide() (line 270) unconditionally does window_->setSlideImage(rasters_[i]). refresh() (line 226) is the ONLY place that honours Mode::Holding / Mode::ConfirmQuit, and this path bypasses it entirely.

**Impact:** Karl opens the deck at the podium and presses Esc to blank the projector while the room settles — exactly the canonical use of the privacy screen. Pre-render is still in flight, so the moment the worker finishes the slide he is standing on, the confidential deck reappears on the wall with no key press and no warning, and stays there until he presses Esc again. Same failure behind the quit prompt: the deck sits visible behind 'Quit the presentation?'. This defeats the TM-002/019 blackout mandate at the one moment it exists for. The window is bounded by pre-render duration (the first seconds after a deck is opened), but that is precisely when a presenter blanks the screen, and it reproduced on the cold-start round every time.

**Fix:** In AppShell::onSlideReady(), always cache the raster but only push it to the window when the mode permits it — replace the `showSlide(...)` call with `refresh()`, which already switches on controller_.mode() and blanks for Holding/ConfirmQuit. Add a widget-level regression test that asserts SlideSurface::lastPaintedRect().isEmpty() after a slideReady delivered while mode == Holding.

### [SEV-2] On a MacBook + projector the deck is letterboxed twice and covers only ~75 % of the projector — and rehearsal on the laptop alone looks perfect

**Repro:** cd /private/tmp/claude-501/-Users-karl-Documents-Claude-Projects-powerpoint-voice/05a4d2ab-f2bc-4839-9c01-2ee22b3c3560/scratchpad
cat > /tmp/screens.json <<'EOF'
{ "screens": [
  { "name":"laptop","x":0,"y":0,"width":1512,"height":982,"logicalDpi":96,"logicalBaseDpi":96,"dpr":2 },
  { "name":"projector","x":1512,"y":0,"width":1920,"height":1080,"logicalDpi":96,"logicalBaseDpi":96,"dpr":1 } ] }
EOF
QT_QPA_PLATFORM="offscreen:configfile=/tmp/screens.json" ./harness/b/presenter_harness "$PWD/decks" s30

STAGE (MacBook Air/Pro 13-14" + 1080p projector):
  >>> raster 3024x1964 (aspect 1.540)   window aspect 1.778   deck aspect 1.778
  >>> surface 1920x1080; slide content occupies 1662x936 at (129,72)
  >>> black bars: left=129 right=129 top=72 bottom=72
  >>> slide covers 75.0% of the projector
MacBook Pro 16" (1728x1117@2) + 1080p: 1670x940, 75.7%.  MacBook Air 13" (1470x956@2) + 1080p: 1660x934, 74.8%.
REHEARSAL, laptop only (QT_QPA_PLATFORM="offscreen:configfile=/tmp/laponly.json"): 1512x851, correct — top/bottom bars only.
Single 1920x1080 screen: 1920x1080, 100.0%, no bars.

Mechanism (three layers compounding):
  1. src/ui/app_shell.cpp:171 — setTarget(renderTargetPolicy(currentScreens())) sizes the raster from the LARGEST screen by device pixels across ALL screens, i.e. the Retina laptop (1512x2=3024 x 1964), not the screen the window is presented on.
  2. src/render/slide_renderer.cpp:181-197 — render() returns exactly targetW x targetH with the 16:9 slide letterboxed INSIDE it (bars baked into the raster).
  3. src/ui/slide_surface.cpp:44 — fitRect(image_.size(), ...) fits by the RASTER's aspect (1.540), not the deck's (1.778), so the already-boxed raster is boxed again into the 1920x1080 window.

**Impact:** Karl's 16:9 deck is displayed at 1662x936 on a 1920x1080 projector instead of filling it: a 129 px black frame left and right and 72 px top and bottom, all text 13 % smaller than it should be, 25 % of the projector area wasted. It looks like the app cannot drive the projector properly. The trap is that it is invisible until showtime — rehearsing on the laptop alone renders correctly, and the fault only appears once a second display with a different aspect ratio is plugged in.

**Fix:** Two independent fixes, either of which removes the visible frame; do both. (a) Size the raster from the screen the presentation window is actually on (recompute on QWindow::screenChanged and on Ctrl+Shift+D), not from max-over-all-screens. (b) Stop double-fitting: either have SlideRenderer emit a raster at the DECK's aspect with no baked bars and let SlideSurface do the single letterbox, or have SlideSurface fit using the deck aspect it is told rather than the raster aspect. Add a geometry test asserting that a 16:9 deck on a 16:9 window covers >99 % of it regardless of what other screens exist.

### [SEV-3] Notices never expire: NoticeClass::Transient is set everywhere and read nowhere, so a message band sits on the projector for the rest of the talk

**Repro:** ./harness/b/presenter_harness "$PWD/decks" s28
  >>> strip right after 'past the end': 'End of deck — slide 10 of 10'
  >>> strip 6 s later, with no further input: 'End of deck — slide 10 of 10'
  [FAIL] a Transient notice cleared itself instead of sitting on the projector

src/present/notice.hpp documents "Transient notices fade; Sticky ones stay until the condition clears", and every notice in presentation_controller.cpp/key_translator.cpp carries a NoticeClass. grep shows nothing outside notice.hpp ever reads `cls`: AppShell::applyResult (src/ui/app_shell.cpp:294) flattens the Notice to a QString in lastNotice_ and refresh() (line 247) re-shows it forever. NoticeStrip paints a 70 %-opaque black band, NoticeStrip::heightFor(1080) = 72 px.

**Impact:** From the first arrow key onward the audience sees a permanent translucent black band across the bottom 72 px (6.7 %) of the projector reading 'Slide 2', 'Slide 3', … It obscures the bottom of every slide, and a one-off message such as 'End of deck — slide 10 of 10' or 'Deck has 10 slides' stays on the wall indefinitely — including through Q&A once he navigates back into the deck.

**Fix:** Honour NoticeClass in AppShell: start/restart a single-shot QTimer when a Transient notice is applied and clear lastNotice_ (plus repaint) when it fires; leave Sticky notices until the condition clears. The tick_ timer already running at 250 ms can drive the expiry.

### [SEV-3] Ctrl+Shift+F (ToggleFullScreen) and Ctrl+Shift+R (ReRenderDeck) are consumed by the key translator and then silently dropped by AppShell

**Repro:** ./harness/b/presenter_harness "$PWD/decks" s21
  >>> Ctrl+Shift+F: fullScreen 1 -> 1
  [FAIL] Ctrl+Shift+F (ToggleFullScreen) actually does something
  >>> Ctrl+Shift+R: raster restored = 0
  [FAIL] Ctrl+Shift+R (ReRenderDeck) actually re-renders

src/present/key_translator.cpp:63-70 produces UiRequest::ToggleFullScreen and UiRequest::ReRenderDeck and sets consumed=true. src/ui/app_shell.cpp:137-162 handles RequestHolding, RequestQuitConfirm, CancelQuit, MoveSlideWindowToNextScreen and ConfirmQuit — ToggleFullScreen and ReRenderDeck fall into `default: break;` on lines 160-161.

**Impact:** Two documented recovery chords do nothing. Because the key IS consumed, there is no fallback either — the press is swallowed with no notice, so it reads as a frozen app. Ctrl+Shift+F is the only documented way out of fullscreen (Esc is deliberately disabled and close is refused), so if Karl needs to leave fullscreen to reach another app mid-talk he is stuck with OS-level window management. Ctrl+Shift+R is the only documented recovery if a slide renders wrong.

**Fix:** Wire both cases in AppShell's uiRequestSink: ToggleFullScreen -> window_->isFullScreen() ? showNormal() : showFullScreen(); ReRenderDeck -> teardown the render worker and restart it against deck_ (PreRenderWorker already has the running_ re-entrancy guard for this, per its own comment). If either is not going to ship for 2026-08-10, remove them from the translator so the key is not consumed and the presenter gets normal behaviour instead of silence.

### [SEV-3] Typed slide numbers give the presenter zero feedback, and the translator's 'slide number too long' notice is dropped by the window

**Repro:** ./harness/b/presenter_harness "$PWD/decks" s22
  >>> after typing '1': strip='' translatorBuffer='1'
  [FAIL] the half-typed slide number is echoed somewhere the presenter can see
  >>> after 8 digits: strip='' buffer='199999'
  [FAIL] the 'slide number too long' notice reaches the presenter

src/ui/presentation_window.cpp:55-60 forwards a.command and a.uiRequest but never reads a.notice, so the Notice{SlideNumberTooLong} raised at src/present/key_translator.cpp:96 has no path to any surface. KeyCommandTranslator::pendingDigits() (key_translator.hpp:53) exists and is never called.

**Impact:** On a 10-slide deck Karl types '1','0',Enter with nothing on screen confirming what he typed. A mistyped digit produces a silent rejection ('Deck has 10 slides' only appears after Enter), and a stuck digit from 3 s ago silently prefixes the next number. He cannot tell a swallowed keypress from a dead keyboard mid-talk, which is precisely the situation the audited keyboard fallback exists to cover.

**Fix:** In PresentationWindow::keyPressEvent, add `if (a.notice && noticeSink_) noticeSink_(*a.notice);` and route it through AppShell to the notice strip (Operator role). Separately, echo translator_.pendingDigits() to the strip on every digit, e.g. 'Go to slide 1_', and clear it on Enter/mode change.

### [SEV-3] The privacy-blackout screen shows the audience an operator instruction that is factually wrong ('any key to resume')

**Repro:** ./harness/b/presenter_harness "$PWD/decks" s25
  >>> on-surface text during blackout: 'Presentation paused — press Esc again to exit, any key to resume'
  >>> after 'P': mode=Holding lit=0.003
  >>> after 'A': mode=Holding lit=0.003
  >>> after 'Enter': mode=Holding lit=0.003
  >>> after 'Space': mode=Presenting lit=0.562

Text: src/present/notice.cpp:35-36 (NoticeId::HoldingHint). It is painted on the AUDIENCE-facing SlideSurface by src/ui/app_shell.cpp:231-233, which asks for NoticeRole::Operator and then draws it on the projector. Only navigation keys leave Holding (src/present/presentation_controller.cpp:117-120), so 'any key' is wrong for P, A, Enter and every non-navigation key.

**Impact:** During the blackout the audience reads an instruction telling them how to exit Karl's presentation, and the instruction is wrong: he presses P or Enter expecting the deck back, nothing happens, and he has to guess. 'press Esc again to exit' is also misleading — Esc goes to a quit prompt, which is then itself displayed to the audience.

**Fix:** Reword to what is actually true and audience-appropriate, e.g. 'Presentation paused' on the audience surface, with the key hints (Esc = quit prompt, arrow/space = resume) shown only on the operator surface when F5 lands. At minimum change 'any key' to 'press the arrow keys or space to resume'.

### [SEV-3] After a failed open on the CLI launch path the app exits with no window — the audit-C3 'never leave the presenter with no window' guard is dead because main.cpp never creates the StartView

**Repro:** ./harness/b/presenter_harness "$PWD/decks" s19    # bad path
  >>> visible top-level windows after the failure: 0  (start_=NULL window_=NULL)
./harness/b/presenter_harness "$PWD/decks" s19b   # decks/zero0.pptx: parses fine, zero slides
  >>>  | That file contains no slides.
  >>> visible windows: 0  window_=NULL
./harness/b/presenter_harness "$PWD/decks" s32    # main.cpp verbatim, real exec() loop
  >>> exec() returned after 152 ms; visible windows = 0; dialogs seen = 1

src/main.cpp:26-30 calls showStart() only in the `else` branch, so `powerpoint_voice deck.pptx` never constructs start_. Both failure paths in src/ui/app_shell.cpp (lines 114-116 and 127-129) then run `if (start_) start_->show();` against a null pointer and do nothing. s32 confirms the app then quits on quitOnLastWindowClosed rather than ghosting.

**Impact:** Karl launches with his deck on the command line (or via a shortcut / file association), the file is the wrong one or is damaged, he clicks OK on the dialog — and the application disappears. He must find a terminal or shortcut and relaunch, in front of the room. The mitigation the code claims for audit C3 is unreachable on the only launch path that can actually open a deck. Mid-talk failures are fine (s11b/s11d: the live window survives and stays navigable).

**Fix:** Call showStart() unconditionally in main.cpp before openDeck(), and have AppShell::showStart() create start_ lazily wherever the failure paths need it (`if (!start_) start_ = new StartView(); start_->show();`). Since StartView currently has no way to pick a file, also give it at least a QFileDialog button — AppShell already includes <QFileDialog> and never uses it.

### [SEV-3] Keyboard focus is not restored to the presentation window after the modal error dialog closes

**Repro:** ./harness/b/presenter_harness "$PWD/decks" s29
  >>> focusWidget before: pptv::PresentationWindow
  [PASS] dialog appeared and was dismissed
  >>> focusWidget after: (none)   activeWindow: (none)
  [FAIL] keyboard focus returned to the presentation window after the dialog

src/ui/app_shell.cpp:107-131 — the two failure paths pop an app-modal QMessageBox parented to nullptr and return without touching window_. The success path (lines 204-207) does raise()/activateWindow()/setFocus(); the failure paths do not.
Honest caveat: this was measured under the offscreen QPA plugin, whose activation model is weaker than a real window manager, so the focus loss may not be as absolute on real hardware. The code observation — nothing re-focuses the window after the dialog — is not platform-dependent.

**Impact:** Karl picks the wrong file mid-talk, dismisses the error, and the arrow keys may no longer reach the deck because the parentless modal dialog took activation and nothing gave it back. The recovery (click the projector window) is not obvious under stage pressure, and on a fullscreen window on a second display it may not be clickable from the laptop at all. The unparented, app-modal dialog is also a stage risk in its own right: it freezes the deck and can land on a different screen from the one the presenter is watching.

**Fix:** Parent the QMessageBox to window_ when a presentation is live (so it is a sheet on the right screen, not a stray top-level), and after it returns call window_->raise(); window_->activateWindow(); window_->setFocus() on the failure paths exactly as the success path does. Better still, replace the modal box mid-talk with a NoticeStrip message so a bad file never blocks a live presentation at all.

### [SEV-4] quitConfirmed_ is never reset, so a deck opened after a confirmed quit is closed by the first key press

**Repro:** ./harness/b/presenter_harness "$PWD/decks" s16
  [PASS] quit confirmed
  [PASS] deck B loaded
  ...  after reopen: quitConfirmed=1 mode=Presenting windowVisible=1
  >>> after ONE arrow key: visible=0 current=2 quitConfirmed=1
  [FAIL] one arrow key did not slam the window shut

src/present/presentation_controller.cpp:14-20 — setDeck() resets slideCount_, current_, jump-undo and mode_, but not quitConfirmed_. src/ui/app_shell.cpp:296-298 — applyResult() closes the window on every dispatch while quitConfirmed() is true. src/ui/presentation_window.cpp:75-78 — closeEvent also stops refusing closes.

**Impact:** Latent today rather than live: in the shipped binary a confirmed quit closes the last window and QApplication exits, and there is no in-app way to open a second deck, so the state is not reachable in v0.1. It becomes a real bug the moment a file-open action, a recent-files list, or drag-and-drop lands on the StartView — the next session would open, show slide 1, and then close itself on the first arrow key, and every close request would be accepted from then on.

**Fix:** Reset the session's quit state where the session is reset: add `quitConfirmed_ = false;` to PresentationController::setDeck(), and add a controller unit test that setDeck() clears it. This is a one-line change worth making now, before the file-open feature makes it reachable.

## Could not break

- Navigating after pre-render COMPLETES (s1) — the site of the previous audit's SEGV. The QPointer<PreRenderWorker> is correctly null by the time the worker self-destructs on its own thread ('renderWorker_ after finish = null'), and 9 forward + 9 backward key presses landed exactly on slide 10 and slide 1 with the projector pixels matching the controller's index.
- The QPointer-vs-worker-destruction race, hammered deliberately (s24): 40 rounds of opening karl10.pptx and spinning Right/Left key presses continuously across the moment pre-render completes and the worker is deleteLater'd on the worker thread. No crash, no dangling invokeMethod, 10/10 rasters every round.
- A 50-key-press burst starting while pre-render is in flight (s2, 40-slide deck): the burst took 0 ms of UI-thread time, the controller clamped correctly at slide 40 (NoMove, not wraparound), and the full pre-render still completed afterwards. The TM-018 'UI thread never blocks on deck content' mandate holds for navigation.
- Jumping to an unrendered slide mid-render (s3): typing 3-5-Enter at slide 35 of 40 put the controller on 35, showed 'Rendering slide 35...' rather than a black screen, re-steered the worker (raster for 35 arrived within seconds instead of at the end), and the rest of the deck still finished.
- Cross-deck content leakage (s9, s9b, s26). I specifically hunted for a stale slideReady from deck A landing after deck B's rasters_.assign(). It cannot happen: teardownWorkers() blocks the UI thread while the old worker finishes, so any straggler slideReady is already queued ahead of the new deck's `loaded` signal and is wiped by the assign. 8 rounds of switching away from a half-rendered 16-slide deck to a 3-slide deck, sampling the projector pixels and the whole raster cache every 5 ms across the transition: zero frames of deck-A content on screen, zero deck-A images in the new cache.
- Typing a slide number and abandoning it (s4): the 3 s staleness rule works through the real key path — a '7' left over from 3.4 s earlier did not prefix a later '5'; and inside 3 s, '7'+'5' correctly accumulated to 75, which the BUG-16 range check REJECTED on a 10-slide deck instead of clamping to 10. Slide 0 and slide 9999999 are likewise rejected (s14).
- The two-step quit and everything around it (s6, s7, s8, s17): Ctrl+Shift+Q alone never quits; the quit prompt is genuinely visible (measured lit pixels), swallows a stray Right without moving the deck behind it, auto-dismisses to Holding at 10 s (not to the deck), and Esc cancels it cleanly with the deck resuming on the next arrow. 30 Escapes in a row never confirmed a quit and the window was still up.
- Close-request refusal (s12): window->close() mid-render is refused while quitConfirmed is false, and the confirmed close takes 0 ms.
- Error-dialog content (s11, s11c) — the TM-013 concern. Every failure produces a fixed string chosen by LoadErrorKind: 'That file is not a PowerPoint (.pptx) file.', 'That file is not a valid PowerPoint deck.', 'That deck is damaged and could not be read.', 'That file contains no slides.' No path, no filename, no attacker-controlled bytes. bad_notzip/bad_nopresentation/bad_malformedxml all handled without a presentation window ever opening.
- Audience-visible notice text (s18): across navigation, an out-of-range jump and a first-slide bounce, the strip only ever showed 'Slide 2', 'Deck has 10 slides', 'Already at the first slide' — integers and fixed strings only, no deck content and no path. The closed Notice vocabulary is doing its job.
- A live talk failing over a bad open (s11b, s11d): opening a nonexistent or hostile deck while presenting leaves deck A loaded, the window visible and fully navigable, with the projector still matching the controller.
- Opening the same deck twice quickly (s10) and six times back-to-back with no wait (s10c): one 10-slide deck, 10 rasters, no window pile-up, navigation correct afterwards.
- Quitting and closing mid-render with a normal-speed deck (s13, s13b): ~AppShell completed teardown in 320 ms, well inside bounds, with no crash. (It is only the >5 s slide that breaks it — SEV-1 above.)
- The full 10-slide talk end to end (s15): every forward step had the projector pixels matching the controller's index, the Q&A blackout held for 1.5 s of no input, Left came back on slide 9, a typed jump to 10 landed, and the deliberate quit ended it.
- Multi-display behaviour (s27): with a laptop + projector configured, the presentation window correctly opened FULLSCREEN ON THE EXTERNAL DISPLAY (audit H5), Ctrl+Shift+D moved it to the other screen and back while staying fullscreen with the slide intact, and moving screens during the privacy blackout did NOT un-blank the projector.
