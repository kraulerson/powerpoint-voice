## How this was validated

The persona's instruction for this step is *"verify every mitigation works, test with attack
payloads, don't sign off unverified."* So the standard applied here is: **a mitigation is not
validated because it exists in the code — it is validated when something demonstrates it
works.**

Five working attack payloads were built for this report and are committed as fixtures
(`tests/fixtures/attack_*.pptx`, generated by `tests/fixtures/generate_fixtures.py`).
They are exploit attempts, not malformed-input fixtures. Each has a test in
`tests/test_deck_loader.cpp` under the `SEC/` prefix, and each of those tests **asserts the
deck actually loads first**, so it cannot pass by the deck being rejected before the payload
is reached.

Where the answer is that the attack surface does not exist, the row says **STRUCTURAL** rather
than "mitigated". That is a stronger claim, and it is also a more fragile one — it stays true
only while nobody adds the surface back. Every STRUCTURAL row therefore has a test that pins
the absence.

**Five new attack payloads** were added to the suite by this validation
(`SEC/TM-004`, `SEC/TM-007`, `SEC/TM-010`, `SEC/TM-010/017`, `SEC/TM-016`).
None of them found a defect — which is a weaker statement than it sounds, and is recorded as
such: they confirm four structural claims that had been asserted since Phase 1 and never
tested.

**The one I would not sign off on myself is TM-021.** No fuzzing campaign has been run against
a parser that reads untrusted archives and untrusted XML, and the four memory-safety defects
found under sanitizers during construction are evidence that the surface is live. For a talk
on Karl's own machine with his own deck the practical exposure is near zero — the only input
is a file he authored. That is a fair reason to accept it and a bad reason to call it closed.
